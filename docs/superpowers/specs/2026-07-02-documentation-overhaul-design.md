# PIGO8 Documentation Overhaul - Design

## Goals & Scope

Make `docs/` (the mdBook site published to GitHub Pages) genuinely exhaustive, accurate, and
visually compelling, closing three gaps identified during review:

1. No complete API reference (only a quick cheatsheet).
2. Content gaps and drift: broken internal links, and mentions of code removed in recent
   cleanup (`frame_metrics.go`, `perf_profiler.go`).
3. Zero visual demonstration of the engine in action (only 4 images exist, all for the editor).

### In scope

1. **API Reference** - a new, exhaustive reference section covering every exported PIGO8
   function/type/constant, organized by domain, generated by walking the actual source so it
   cannot drift from reality.
2. **Content audit & gap-filling** - fix broken links, verify every code sample and claim
   against current source, remove references to anything deleted in the recent cleanup, add
   missing pages (FAQ/Troubleshooting, Testing Your Game).
3. **Visual capture tooling** - a new `cmd/docshots` tool that builds each example to WASM
   (reusing `cmd/webexport`), drives it headlessly via Chrome DevTools Protocol (`chromedp`),
   captures canvas frames while scripting keypresses, and assembles them into GIFs/PNGs
   embedded into the relevant docs pages.
4. **Navigation & consistency** - a consistent per-page template (intro -> concept -> example
   -> see-also) and an updated `SUMMARY.md`, plus light branding (favicon/logo wiring, subtle
   accent color).

### Explicitly out of scope

- Rewriting/renaming the public Go API itself.
- Versioned docs (multiple API versions side by side).
- A full custom mdBook theme rewrite - only light branding via mdBook's existing
  `[output.html]` support (favicon, logo, additional CSS).
- Multi-language/i18n docs.
- Wiring visual capture into the `mdbook.yml` CI pipeline - it's a manual/occasional
  regeneration step, with generated assets committed to the repo.
- Chasing 100% godoc comment coverage in the Go source itself, beyond what's needed to write
  accurate reference entries.

## Workstream 1: API Reference

### Structure

A new top-level SUMMARY.md section, "API Reference", with one page per domain, mirroring the
existing conceptual sections:

```
docs/reference/api/
├── 00-overview.md        # how to read the reference, conventions
├── 01-screen-drawing.md  # Cls, Pset, Pget, Line, Rect(fill), Circ(fill), Print, shapes
├── 02-colors-palette.md  # Pal, Palt, Color, palette management
├── 03-sprites.md         # Spr, Sspr, Sget, Sset, Fget, Fset
├── 04-maps.md            # Map, Mget, Mset
├── 05-input.md           # Btn, Btnp, mouse, gamepad
├── 06-audio.md           # Music, MusicLoop, StopMusic, F32 variants
├── 07-camera.md          # Camera
├── 08-collision.md       # ColorCollision, MapCollision
├── 09-math.md            # Flr, Rnd, Sqrt, Sign, Time, etc.
└── 10-settings-lifecycle.md  # Settings, NewSettings, InsertGame, Play, PlayGameWith, Cartridge
```

### Per-function entry format

```markdown
### `Spr(n int, x, y float64, args ...float64)`

Draws sprite `n` at position `(x, y)`.

**Parameters:**
| Name | Type | Description |
|------|------|--------------|
| `n` | `int` | Sprite index (0-255) |
| `x`, `y` | `float64` | Top-left position in screen pixels |
| `w`, `h` | `float64` (optional) | Width/height in sprites (default 1,1) |
| `flipX`, `flipY` | `bool` (optional) | Flip horizontally/vertically |

**Example:**
​```go
p8.Spr(1, 10, 20)              // draw sprite 1 at (10,20)
p8.Spr(1, 10, 20, 2, 2)        // draw as a 16x16 region
p8.Spr(1, 10, 20, 1, 1, true)  // flipped horizontally
​```

**See also:** [Drawing Sprites](../../20-sprites/01-drawing-sprites.md)
```

### Generation approach

Walk the actual exported Go source using `go/doc` (or `go doc -all`) against the `pigo8`
package to get the real, current list of exported functions/types/constants with real
signatures and existing godoc comments as a starting point. Expand each into a full
description, parameter table, and example, cross-checked against existing conceptual docs and
tests so examples are correct and runnable. This guarantees the reference can't miss a function
or list a stale signature.

The existing cheatsheet stays as-is (fast lookup, one-liners); the API Reference is the deep,
exhaustive version with explanations and examples. Add a one-line cross-pointer between them.

## Workstream 2: Content Audit & Gap-Filling

### Audit pass

1. **Link check**: crawl every internal markdown link in `docs/` and verify the target exists.
   Known issues to fix: `docs/editor.md` links to `installing_go.md` (should be
   `../01-installation.md`) and `embedding.md` (should be
   `90-advanced/01-resource-embedding.md`).
2. **Dead-API check**: grep all docs for references to symbols/files removed in the recent
   cleanup commit (`frame_metrics.go`, `perf_profiler.go`, related metrics functions) and
   update or remove those mentions.
3. **Signature check**: cross-reference every code sample against real function signatures
   (via the same `go/doc` pass used for the API Reference) to catch drift.
4. **Tone/consistency pass**: light copy-editing so every page matches the existing good voice
   (`introduction.md`, `03-game-loop.md`) rather than inventing a new one.

### New pages

- `docs/reference/faq.md` - Troubleshooting & FAQ: common install/build errors (CGO/compiler
  issues, blank screen, WASM build failures, audio not playing on Linux, sprite not showing
  up), with concrete fixes.
- `docs/90-advanced/03-testing.md` - Testing Your Game: how to unit-test game logic decoupled
  from `Update`/`Draw` (PIGO8 games are plain Go structs, so standard Go testing applies) -
  patterns for testing collision, state transitions, etc.

## Workstream 3: Visual Capture Tooling

### New tool: `cmd/docshots/main.go`

A Go CLI that generates a screenshot or GIF for a given example.

**Pipeline per example:**

1. Reuse `cmd/webexport`'s build logic to compile the example to `game.wasm` + `index.html` +
   `wasm_exec.js` into a temp directory.
2. Serve that temp directory over a local HTTP server (`net/http`, ephemeral port).
3. Launch headless Chromium via `chromedp` (`github.com/chromedp/chromedp`, pure Go),
   navigate to the served page, wait for the `<canvas>` element to appear (Ebiten inserts it
   dynamically).
4. Run a scripted input sequence per example (declared per-manifest-entry, e.g. "press Right
   for 1s, then Down for 1s") dispatched via synthetic keyboard events, sampling the canvas
   every ~100ms via `canvas.toDataURL('image/png')` through `chromedp.Evaluate`.
5. Decode captured base64 PNG frames in Go:
   - Static feature -> save the single best frame as a PNG.
   - Animated feature -> assemble frames into a looping GIF via `image/gif`.
6. Write output to `docs/img/generated/<example-name>.{png,gif}`.

### Manifest-driven configuration

Each capture job is declared in `cmd/docshots/manifest.go`: example dir, output name,
static-or-gif, input script, capture duration. Keeps `main.go` generic and makes it easy to
add/regenerate entries later.

### Target embed spots (~10-12)

Hello world, sprite animation, spritesheet regions, map rendering, map layers, camera
movement, palette effects, color/map collision, the Pong tutorial, and the editor (already has
images) - each mapped to the best-demonstrating example under `examples/`.

### Failure handling

If Chromium/chromedp isn't available in an environment, the tool exits with a clear error
rather than producing broken output. Regeneration is a manual step (`go run ./cmd/docshots`),
not part of `mdbook build` or CI. Generated assets are committed to `docs/img/generated/`.

## Workstream 4: Navigation, Consistency & Light Branding

### Per-page template

1. One-paragraph intro: what this covers and why it matters.
2. Core concept explanation with inline code snippets.
3. At least one complete, runnable example where the topic warrants it.
4. Embedded visual where one was generated (Workstream 3).
5. A `## See Also` footer linking to the matching API Reference page and 1-2 related
   conceptual pages.

Existing pages that are already solid get retrofitted (mostly adding `See Also` footers and,
where relevant, a visual) rather than rewritten.

### SUMMARY.md changes

Add the "API Reference" section and the two new pages in logical positions:

```
# Reference
- [Cheatsheet](reference/cheatsheet.md)
- [API Reference](reference/api/00-overview.md)
  - [Screen & Drawing](reference/api/01-screen-drawing.md)
  - ... (per Workstream 1 domain list)
- [PICO-8 Comparison](reference/pico8-comparison.md)
- [FAQ & Troubleshooting](reference/faq.md)
```

`Testing Your Game` slots into "Advanced Topics" alongside Resource Embedding/Web Export.

### Light branding

Wire up `docs/logo.png` as the mdBook favicon/logo via `book.toml`'s `[output.html]` section
(currently absent). Add a subtle PICO-8-esque accent color via mdBook's `additional-css`
support if low-risk. No custom theme rewrite.

## Validation & Rollout

### Validation before calling this done

1. `mdbook build` succeeds with zero broken-link warnings.
2. A link-checker pass confirms every internal `.md` link and image reference resolves.
3. Every code sample meant to be a complete program is verified to `go build`; inline
   fragments are checked against real signatures from `go/doc`.
4. `go vet`/lint passes on the new `cmd/docshots` tool, held to the same bar as the rest of the
   codebase (proper error handling, table-driven tests for helpers like GIF frame assembly).
5. Manual spot-check via `mdbook serve` that embedded images render correctly and aren't
   broken/oversized.

### Rollout sequence (maps to implementation plan phases)

1. Content audit + fix broken links/dead references.
2. Build the API Reference, one domain page at a time.
3. Add the two new pages (FAQ, Testing).
4. Build `cmd/docshots`, validate end-to-end on one example.
5. Generate and embed visuals across the target spots.
6. Retrofit consistency (`See Also` footers) + `SUMMARY.md` + light branding.
7. Final validation pass (link check, `mdbook build`, spot-check).
